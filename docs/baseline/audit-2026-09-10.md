## 2. 所有 remote loader 與 Edge Functions

正式入口 `index.html` 的 `millionproject-remote-update-loader` 以 `fetch` 取得 `millionproject-patch?ts=...`，`cache: no-store`，再執行 `(0,eval)(code)`。主 patch 再依下面順序逐一 fetch／eval；URL 上的 `v=36` 只是查詢字串，程式沒有依它挑選固定版本。

**固定載入順序：** quality → features → cards → shell → runtime → icons → card-guard → investment-core → investment-guard。

主 loader 為 698 bytes，9 個必要模組 response 合計 147,496 bytes；另有 176,346 bytes 基底 HTML、Supabase JS CDN 與字型資源。9 個模組 sequential fetch，在模組間有相依與覆寫；任何一個失敗只記錄 console error，仍繼續載入後面的模組，可能形成新舊功能混用。主入口 loader 沒有整體完成／失敗的可驗收狀態。

## 3. 資料一致性發現與優先順序

### P0：遷移前必須有清楚的防護與驗收

**A. 版本不可重現、只能回滾部分產品。** 相同 GitHub SHA 可以因 Edge Function 被更新而呈現不同功能。rollback Vercel 不能同步 rollback 遠端 JS、RPC 或 schema。現有主 loader 不固定 response hash，個別模組錯誤仍繼續；不能直接換成只載入 GitHub 舊 HTML。

**B. 信用卡識別不一致，已有具體觸發條件。** `runtime.fillCards()` 將 `card_name || issuer` 放入快速操作選單；`mp31Save()` 只保存 `payment_method` 字串。`cards.mpCreditCards()` 卻以 `payment_method === issuer` 計算刷卡與額度。當 card_name 不同於 issuer，從快速操作選擇卡片名稱的消費可能漏進卡片帳單。這個原始碼缺陷不等於已確認所有歷史紀錄漏算；公開交接不包含使用者的實際明細或筆數。schema 雖已有 credit_card_id，主流程尚未一致使用。先建立穩定 ID，再以可稽核對照處理舊字串；同銀行多張卡不可猜配。

**C. 結帳日當天比較有實際可重現的邊界偏差。** 正式 cards 的 `parse()` 將刷卡日設為當地 12:00，結帳日 dateInMonth 為 00:00，之後使用 `d <= thisEnd`。card-guard 的預覽有相同模式。以正式 endpoint 提取的純日期函式，在 Asia/Taipei 執行：

| 刷卡日 | 設定 17 日結帳的計算結果 | 設定 24 日結帳的計算結果 |
|---|---|---|
| 2026-09-16 | 2026-09-17 | 2026-09-24 |
| 2026-09-17 | **2026-10-17** | 2026-09-24 |
| 2026-09-18 | 2026-10-17 | 2026-09-24 |
| 2026-09-24 | 2026-10-17 | **2026-10-24** |

需明確採用「本系統日期制，結帳日當日歸本期」規則後統一純日期比較；真實銀行入帳例外可保留校正機制。資料庫目前台新 17/2、富邦 24/9、國泰 24/9 均符合使用者要求，問題不在設定值。

**D. 行情同步為未驗證使用者的寫入 endpoint。** market-sync 的 GET/POST 沒有檢查 caller，直接以環境中的 service role 讀取全部使用者 portfolio/research_assets/investment_plans，更新 market_prices 與個別市值。對外回應包含缺少行情的 symbol 清單。應將排程及手動同步的身份、頻率、作用範圍分清楚；現階段先保存原始碼，不在唯讀 audit 期間變更設定或觸發同步。

### P1：資料模型與既有行為需要固定契約

**E. 投資主要寫入已具原子性，但還不完整。** 已查核 `save_investment_trade`、`delete_investment_trade`、`rebuild_investment_holding`、`save_opening_holding`、`delete_opening_holding`。皆採 invoker，主要函式使用 auth.uid() 與固定 search_path。交易新增／修改／刪除會在同一 RPC 中同步 finance entry 並重建持倉；修改標的時也重建舊／新標的。期初成本與交易投入金額會合併計算平均成本。這是應保留的核心設計。

仍需修正或驗證：

- 月度 snapshot 由前端另行 persist，錯誤只 console.warn，沒有和交易同一 transaction。
- `portfolio`、`investment_transactions` 與 `finance_entries` 仍可直接由 authenticated 使用者操作自己的資料，沒有交易表重建 trigger；繞過 RPC 的舊寫入路徑可以產生失配。不能在確認所有 caller 前貿然收緊 grants。
- rebuild 使用讀取後 insert/update；目前沒有同使用者同標的的 transaction lock。並行買入／修改可能有競爭，需以隔離資料庫的並行測試證明。
- `plan_id`、`finance_entry_id` 的外鍵只有 ID，沒有 owner 複合約束；RPC 沒有明確驗證 plan 所有人，需確認關聯資料的 ownership。
- `trade_price` 留白時 UI 以 amount/quantity 推估；雖然資料庫會保存正數，但沒有「實際成交／推估」欄位區分。
- fees 有欄位但主要 save RPC 沒有接收它；成本目前依 amount 加總。須固定 amount 是否包含費用，避免遷移時重複加計。
- investment-core 查詢月底用 `YYYY-MM-31`，guard 透過暫時 Proxy 包住共用 `c.from` 修補。這段應改成單一日期工具，避免共用 client 在 await 期間被多個流程改寫。
- 多處 today/month 使用 UTC ISO，00:00–07:59 台灣時間可能落到前一日／前一月；信用卡與投資須共用 Asia/Taipei 的日期契約。

**F. 交易與計畫分離方向正確。** investment_plans 獨立儲存，mpRunPlan 開啟買入表單；不會因計畫建立自動產生已成交持倉。交易 side 目前資料庫限制僅 buy，遷移不能暗中加入未設計的賣出成本算法。查核時 plans、transactions、portfolio 與 investment finance entries 的實際 count 均為 0，因此不能以真實持倉計算過關作為證據。

**G. 月結估值仍有多份來源。** `moneyEngine()` 讀取 portfolio.current_value，缺值時可能以成本代替，並混入 untrackedInvestment；投資頁則優先讀 market_prices。兩個畫面可能採不同估值。回算歷史月份時 moneyEngine 仍使用最新 portfolio；跨月交易更動不能用今日價格覆寫過去月底快照。須定義閉帳／未閉帳狀態、估值日、缺價狀態与快照計算版本。

**H. 信用卡費不重複支出的方向正確，但帳款計算不完整。** 刷卡存 finance_entries expense；繳款只存 credit_card_payments。現行帳單只算當期與上一已結帳期，更早未清餘額可能不在可用額度中；繳款清單只展示最新 8 筆，沒有可見分頁。因此「有 edit/delete function」不等於所有歷史紀錄都可操作。應以每個 cycle 的應繳、已繳、未清餘額重建，而不是只看 prevClosed。

### P1：行情來源與價格升級

market-sync 使用 TWSE `STOCK_DAY_ALL`、TPEX `tpex_mainboard_quotes`；台灣 13:35 後，當日正式日行情未出現才接受當天 MIS 最後成交價，保存 provisional_close 與 source_time；當次執行已取得當日正式價格時不再用 MIS 覆蓋。這部分方向符合需求。

仍有缺口：

- 每次同步直接 upsert，沒有和資料庫既有 price_date/status 比較；舊批次或較晚完成的請求可能把較新／正式價格覆蓋。
- TWSE 或 TPEX 任一上游失敗會使整次同步失敗，缺少逐市場的部分成功策略與 timeout。
- price table 只有 symbol 一筆，未保存每日價格歷史，不足以還原歷史月底估值。
- investment-guard 以「最新日期那一組價格」判斷整張卡片正式／暫定，較舊或其他標的 provisional 可能被整體正式標籤遮蔽；應逐標的顯示。
- quote/search 路徑仍指向 investment-board，其中 quote 使用 Yahoo。正式 portfolio 已被 investment-core 接管，但市場研究的 loadQuotes/searchQuote 仍有這條路徑，尚不能稱全站行情已完全統一為官方來源。

目前 cron：`15,45 6-9 * * 1-5`，cron.timezone=GMT，也就是台灣週一至五 14:15、14:45、15:15、15:45、16:15、16:45、17:15、17:45。查到 6 筆近期 run 為 succeeded；command 使用 http_get 且未檢查 HTTP status，所以 succeeded 只代表 SQL 呼叫完成，不能證明行情成功更新。

若投資／研究追蹤集合為空，market-sync 會提前回傳 No symbols to sync，因此舊 cache 留存不能單獨判定排程失效；未被追蹤的 provisional cache 也沒有保證升級為正式價。公開交接不包含使用者追蹤標的或實際持倉。

### P2：UI、效能與可維護性

- GitHub 同一 HTML 內已有多次宣告覆寫：monthly 4 次、overview 3 次，另有 portfolio、投資買入及明細 CRUD 的重複宣告。
- quality 與 features 內嵌的 quality 共用 guard；目前 quality 先載入，後一份內嵌段落跳過。不可僅依檔名拆開後換順序。
- render 被 quality、features、budget、shell 多層包裝；另外有 timer、事件 capture 與 DOM observer。分析與整理必須追到最後生效的函式。
- runtime 的 q 快取 key 不含 user，寫入後也沒有立即失效；250ms 內的 render 可能讀到剛才的資料。雖然時間短，仍需定義失效與帳號切換行為。
- card-guard 監聽 #app subtree，preview 會再修改 DOM；存在觀察器再次觸發自身工作的可能，登入後需量測。
- 本次在正式主鏈 payload 與基底 HTML 沒找到 startViewTransition；仍有多層重繪與 timer，不能據此宣稱效能完全合格。

## 5. 安全遷移順序與每一階段的停止條件

**階段 0：補齊存取與建立完整基準。** 先重新取得 Vercel scope `z9000282-8151` 的讀取權，確認 project ID、Git repository 綁定、production branch、root/build/output 設定、production alias 目前 deployment、commit、build log、deployment protection 與環境變數名稱／target（不輸出值）。在隔離測試帳號或隔離環境補齊手機與登入後基準。不得因等待授權而修改任何正式功能。

**階段 1：只收回 source，不啟用新路徑。** 從重新驗證後的 main 建立 migration 分支。將 22 個函式的 source、實際 payload、平台版本與 hash 盤點；活躍與歷史函式分清楚。將 26 筆實際 migration 內容與目前 schema／RLS／RPC／cron 定義匯出並對照，形成能在空測試 DB 重建的版本。不要把線上 schema 全量 DDL 重跑到 production。第一個 PR 只新增可審查的原始碼、契約與驗收工具，不改正式 HTML 的 loader；Vercel production 維持原行為。

建議 repository 逐步形成 `src/`、`supabase/functions/`、`supabase/migrations/`、`tests/`、`docs/audit/`；保留 vanilla 架構可行，這項遷移沒有引入大型框架的必要。壓縮／base64 包裹還原為可讀 source；特別是 investment-core 的 Deno 轉譯後 response 與 payload.ts 要分別保留 hash，不能假設兩者逐字相同。

**階段 2：建立可重現的前端 release。** 把當前正式有效的 9 個 browser payload 作為第一份固定基準，在 preview 以同來源、固定檔案 hash 的 classic scripts 執行，保留有效順序與共享 global lexical scope。此時直接改成 ES modules 可能使 c/u/tab/render 等關係失效，應留待拆模組階段處理。用單一入口選擇完整 legacy 或完整新 release，禁止同一模組同時從遠端和 GitHub 載入。初次切換不順便重畫 sidebar 或更改資料算法。

門檻：基底 DOM、7 個主模組＋設定、桌機 sidebar、手機底部導覽／更多、快速操作、資料讀取與錯誤狀態均一致；必要 module hash 可驗證；初始化完成只有一個可判斷的結果。只通過首頁 HTTP 200 不足。

**階段 3：依資料領域逐批修正。** 先信用卡 ID 與日期工具，再投資 RPC／月結，最後統一行情來源與升級規則。每個 PR 只改一個領域，可在完整 release 中切換該領域的唯一實作。新增 schema 採 expand → 兼容舊讀取 → 可重入回填 → 核對 → 切換 → 日後移除舊欄位；同批不能刪舊欄位或大量改寫金融紀錄。

- 信用卡：先補全新增路徑的 card_id；唯讀產生舊資料對照與歧義清單；可確定才回填。停用卡保留歷史關係。
- 投資：保留 RPC 原子更新，增加 owner、並行鎖／可重試策略；固定成本與費用契約；將跨月快照的待重算狀態與結果可追蹤。舊持倉與真實交易保持可區別，不自動從計畫造交易。
- 行情：函式 source 由 GitHub 管理，Supabase 繼續執行排程／行情服務。寫入前比較交易日與同日狀態優先序：較新日期優先；同日 official 高於 provisional；較舊請求不得降級。保存歷史價格與逐標的狀態；手動同步與排程都記錄 response status、同步數與來源日期。

**階段 4：消除覆寫與重複 render。** 資料契約固定後，將 renderer、事件、日期、repository/service 與 UI 分開。取消 quality 重複內嵌、共用 c.from Proxy、字串 onclick、多層 render 包裝及可自觸發 observer。每個畫面只保留一個 render 入口，mutation 完成後明確失效相關查詢與 refresh 一次，錯誤不能轉成空資料而顯示成功。

**階段 5：正式切換與退役。** 每次發佈記錄 Git SHA、前端 artifact hash、Supabase 函式版本／hash、schema 版本、deployment ID。通過 preview 驗收才進 production；發佈後重讀 production alias 的 HTML／release manifest、必要 assets、API 的 schema 與狀態，並用測試帳號驗收桌機與手機。確認正式主站不再請求 remote JS loader 且持續觀察一段時間後，才依 logs 判定舊函式是否可退役。診斷函式先改成驗證當前 release 清單；不能用現有 module-check 當 release gate。

官方流程依據：[Supabase Functions GitHub 部署](https://supabase.com/docs/guides/functions/deploy)。建議只部署當次變更且已驗收的函式，避免不必要地重部署歷史函式。
